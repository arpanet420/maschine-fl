# Project review, 2026-10-21

A pass over the whole project (FL script, mk3d, every rendered page, docs, tooling) after the
LIVE and pad-activity work, looking for what to make better and what we have learned on the way.
Nothing here has been changed yet; each item names where it is. Ordered by priority inside each
section.

## The lessons (what changed how we should work)

1. **Image-Line's and NI's own FL scripts are on this machine and are the best API reference.**
   `~/Documents/Image-Line/FL Studio/Settings/Hardware/` has `Akai FL Studio Fire/device_Fire.py`
   (performance mode, channel activity, display zones) and `NI Komplete Kontrol/` (NI's 2026 FL
   integration, MIT licensed, a multi-file package). LIVE only started to make sense once we
   copied the Fire's calls. Read them before guessing at an API.
2. **Searching function names misses features that are flags.** The "no native scene trigger"
   conclusion came from diffing function names; the scene trigger is `TLC_ColumnMode`.
3. **Aggregated or "simplest" values hide the state we need.** `LB_Status_Simplest` reported
   scheduled and playing both as 2, and two builds read that as "working".
4. **Log both directions before a hardware test.** Two rounds were lost because outgoing
   triggers and LIVE_GRID had no log line.
5. **Reloading the FL script is View → Script output → Reload script.** MIDI Settings → Update
   MIDI scripts did not reload it (no GOODBYE in the log). `docs/setup.md` still says the wrong one.
6. **Generate wire fixtures from the encoder**, never by hand (several hand-typed hex vectors were
   wrong this week).

## A. Before tomorrow's hardware test

1. **Done 2026-10-21** (LIVE_SECONDS 50 ms, ACTIVITY_SECONDS 40 ms, `OnUpdateLiveMode`, a trigger reads
   at once). **LIVE and ACTIVITY were polled on every service pass, and a pass runs about every 10 ms.**
   NI's script counts OnIdle at ~10 ms ("every 3 OnIdle calls (~30ms)"). `read_live_grid`
   makes about 200 FL calls per pass (8 tracks × 16 statuses + colors + name, color, mute,
   solo, snap), so on the order of 20,000 calls a second while LIVE is open; ACTIVITY adds 16
   per pass while FL plays. Unmeasured, but it is FL's UI thread. Fix: throttle both to every
   3–5 passes (NI does this for its polling), and drive LIVE from FL's `OnUpdateLiveMode`
   callback (the Fire implements it) plus a slow fallback poll.
   `fl-script/MK3Bridge/device_MK3Bridge.py` `service()` and `read_live_grid`.
2. **Reload instruction fixed 2026-10-21.** **`docs/setup.md` gave the wrong reload instruction** ("MIDI Settings → Update MIDI
   scripts"); `docs/handoff.md` has the right one. Its "Controls (phase 4)" table is also from
   phase 4 (CCs 102–107 only).
3. **Nothing has been committed since the public snapshot**: 25 files changed or new (LIVE,
   ACTIVITY, the LIVE screens, docs). PLAN.md's rule is small commits; suggested split: LIVE
   trigger fix, pad activity, LIVE screens, docs. Run `npx prettier --write` first (see F1).

## B. Bugs and wrong text people see

1. **SCENE and ARRANGER tell the user to press a button that no longer exists**:
   `NO_MARKERS_TEXT = "No markers — ADD MKR sets one at the play position"`
   (`src/modes/markerPage.ts:45`), but ADD MKR was removed (`docs/mapping.md` says so twice and
   quotes the old text). Say "add markers in FL" instead.
2. **The page stack's header still describes the first, wrong LIVE**: "one playlist track's
   blocks on the pads" (`src/modes/pageStack.ts:41`).
3. **The FL script header states the wrong color byte order**: "FL colors are 0x--BBGGRR …
   colors are swapped" (`device_MK3Bridge.py:35`), while `fl_color` and the checkpoint 5 result
   say 0x--RRGGBB and nothing is swapped. `MAX_LIVE_BLOCKS`'s comment still says LIVE_GRID.
4. **`plugins.getParamName` focuses the plugin's window** (NI's script: "this flag fires
   spuriously when getParamName focuses a plugin window"). Our name scan calls it up to 4,240
   times per plugin, and `HW_Dirty_FocusedWindow` feeds the editor-follow bookkeeping
   (`note_focus`, `seen_open`). That may be why "follow" felt unclear to the owner
   (PLAN.md 2026-10-18). Check: log `note_focus` during a scan.
5. **The probe calls `getLiveStatus` with `LB_Status_Simplest`**, which the stubs allow only for
   `getLiveBlockStatus`; the Fire calls it with `LB_Status_Simple`. Likely the "Index out of
   range" error that is still listed as open.
6. **No `PME_System_Safe` check.** The Fire triggers clips only when
   `event.pmeFlags & PME_System_Safe`. Our script makes system changes (saveUndo, setGridBit,
   markers, triggerLiveClip) from OnSysEx without looking. No failure seen yet; worth a log line
   when the flag is missing, before deciding anything.
7. **Done 2026-10-21: `channels.getActivityLevel` seen on hardware**, `> 0` flashes per hit, no
   threshold needed.

## C. Trials and probes that have served their purpose

1. **The playlist probe carries finished experiments**: the `ilmcp` import and browser listings
   (settled: not importable from a controller script), a piano-roll script that writes
   `mk3_notes.txt` to the temp folder, and five guessed `getBlockSetStatus` rectangles
   (`probe_lines`, `device_MK3Bridge.py:1353`). Note: **`patterns.getBlockSetStatus` is not a
   dead end**. The Fire calls it as `(left block, top track, right block, bottom track)` for
   its overview mode, and uses the result (0–2) as "empty / has clips / playing". That could
   give LIVE a cheap zoomed-out overview of a large playlist.
2. **SHIFT + DOUBLE's `double_pattern_native` trial** is now what DOUBLE does anyway; the
   step-copy fallback (`double_job`) only matters for an FL without `duplicatePatternData` and is
   the path that adds short notes on piano roll channels.
3. **The browser trial rounds** (`navigateBrowser`, `toggleBrowserNode`, Enter, item menu,
   `selectBrowserMenuItem`, `previewBrowserMenuItem`) did not work; the plugin picker did. Keep
   the picker and drop or hide the rest, with BROWSER_NODE's PROBE chatter.
4. **Every setter still queues a verification PROBE line** (pattern length, color, loop,
   create, double, transpose, perform). The units are verified; move these behind
   `MK3D_PROBE=1`.

## E. Polish on the device

1. **Use FL's own reference calls we do not use yet** (from the Fire): `playlist.liveDisplayZone`
   / `OnDisplayZone` (FL outlines what the MK3 covers), `getTrackActivityLevel`,
   `channels.showGraphEditor` + `getStepParam` (the STEP page's missing held-step velocity and
   pitch editing), `ui.setHintMsg` (show what the MK3 just did in FL's hint bar).
2. **BROWSER on plugins whose real presets live in the plugin**: each step renames the channel
   and adds an undo step (owner's log). Detect generic program names (`Program 1`, …) and say
   so on the screen instead of offering 128 identical-looking programs.
3. **LIVE**: the `M` badge is hard to read (grey on grey); only tracks 1–8; an overview via
   `getBlockSetStatus` (C1); `getLiveTrigSnap` values still to be mapped from the log.
4. **Empty right screens** on BROWSER "no presets", "added" and "picker closed": room for the
   selected channel or a hint.
5. **ACTIVITY redraws the screens** on every change (`src/main.ts` change handler); it only
   changes pads. Skip `updateScreens` for it, as for meters.

## F. Tooling and code health

1. **Prettier drift**: `npx prettier --check src test` fails on 11 files (10 from this week).
   There is no single check script and no CI. Add `npm run check` (typecheck, lint,
   `prettier --check`, `test`, `test:fl`) and, once the repo is public, a GitHub Actions job.
2. **`pagepng` misses the core pages**: CHANNEL, PLUG-IN (NKS and generic), MIXER on its own,
   STEP, PAD MODE / MUTE / SELECT / SOLO, DUPLICATE and the waiting screen. The README images
   for STEP come from an old tool, and `out/` keeps stale PNGs of removed pages
   (`ui-arranger-bank2`, `ui-arranger-none` show the deleted marker controls). Clear `out/ui-*`
   before writing, and add the missing scenes.
3. **Outgoing commands are logged ad hoc** (a special case for `triggerLiveClip` in
   `modeContext.send`). A `--log-fl` flag that logs every command sent would have saved this
   week's blind rounds.
4. **The FL script is one 3,800-line file "because of the symlink"**, but FL loads sibling
   modules from a script's folder (the Fire imports `harmonicScales.py`; NI's is a package) and
   the whole `MK3Bridge` folder is linked. Splitting codec, probe and bridge is possible; the
   5,000-line test file could follow. Try with one small module first.
5. `package.json` has `"private": "true"` (a string; npm expects `true`).
6. Still open from Phase 7: the config file, and robustness (FL restart, unplug, sleep/wake).
